* Design
- Model :: =model.Conflict= gains =ID int64= and =ResolvedAt *time.Time= (nil = unresolved; JSON =null=). Additive fields only; existing JSON consumers see two new keys.
- Store :: =ListConflicts= also selects =id= (stable row IDs surfaced). New =ResolveConflict(ctx, id) (model.Conflict, bool, error)=: a single =UPDATE conflicts SET resolved_at = ? WHERE id = ? AND resolved_at IS NULL= followed by =SELECT= of that row; =false= means "no unresolved conflict with this ID" (unknown ID or already resolved) with *zero mutation*. The =AND resolved_at IS NULL= predicate makes resolution idempotent and never resurrects an already-resolved row. The repository is never deleted.
- CLI :: =forge-sync conflicts= keeps listing unresolved rows (now with IDs); =forge-sync conflicts resolve <id>= resolves exactly that row and prints the resolved row (with =resolved_at=) as the audit confirmation; a non-integer ID or wrong arity is a usage error; an unknown ID fails loudly without mutating. Usage string updated.
- Dry-run discipline :: the only caller of =ResolveConflict= is the explicit operator command; the reconcile engine, webhook server, and scheduler never resolve. No =--dry-run= interaction needed because resolving is itself the explicit, non-automated action.
- No auto-resolution :: nothing in =Plan= or the reconcilers consults =resolved_at=; the #6 human-aligns-one-forge contract is unchanged — resolving a =git-ref-divergence= row only clears it from the unresolved surface after the human has aligned the forges by pushing the winning SHA (ordinary fast-forward then converges).
- Compatibility :: no schema change (existing column); =conflicts= JSON gains =id= and =resolved_at=null= keys; =inspect= embeds the enriched conflict objects; historical rows get IDs on open (autoincrement persists) so the first =forge-sync conflicts= listing already shows actionable IDs.
- Rejected alternatives :: deleting rows after resolution (violates scope guard and auditability); a =resolved_by/-note= audit column (schema change beyond the smallest coherent change); auto-resolving when the two forges now agree (heuristic resolution is explicitly out of scope — the operator decides what "resolved" means).

* Adversarial review
- Race: two operators resolve the same ID concurrently :: the =WHERE ... AND resolved_at IS NULL= predicate means exactly one UPDATE wins; the loser sees 0 rows affected and gets a clean "not unresolved" failure. No double-write, no corruption.
- Race: resolution vs. a concurrent re-recording of the same divergence :: =AddConflict= uses =ON CONFLICT DO NOTHING= keyed on the SHA tuple, so a re-observation of the *same* divergence cannot create a second row or clear =resolved_at=; a *changed* SHA pair is a genuinely new conflict and gets a new row — correct, because the divergence is factually new.
- Accidental mass resolution :: the CLI resolves exactly one ID per invocation; no wildcard/batch path exists to misuse.
- Unknown/typo IDs :: fail loudly with a non-zero exit and no DB change (tested).
- Auditing :: resolved rows stay in the table with =resolved_at= set (verified by reopening the store and by the returned conflict); the unresolved list and the =forge_sync_conflicts= metric exclude them.
- Stable IDs :: autoincrement IDs never change; the unique-tuple dedup keeps a given divergence pinned to one ID across reconciliation cycles, so "stable row ID" holds in practice.
